Complete Audit Table of 14 Form Defects

Includes 2 Alternative Solutions with Architectural Justification

The table below analyzes every line of the bad form, detailing the user-side failure, accessibility barrier, standard fix, and alternative architectural solutions.

# Bad Line of Code Why it is a problem for the user How we fixed it & Alternative fixes
1 <input type="text" placeholder="Your name"> Missing <label>, id, and name.
Screen readers cannot announce what this input is for. Placeholders disappear upon typing, straining user working memory. Without a name attribute, the customer's name is never transmitted to the server! 		Implemented Fix:
Added explicit <label for="customerName">Your name</label>, added id="customerName" and name="customer_name".
2 <input type="text" placeholder="Email"> Wrong input type (type="text") and missing label.
Mobile keyboards will not display the @ key or domain shortcuts, forcing manual keyboard switches. The browser cannot validate email formatting natively. 		Implemented Fix:
Changed to type="email" with connected <label for="customerEmail">Email</label>, name="customer_email", and autocomplete="email".
3 <label>Phone</label><input type="text" id="phone"> Disconnected label and generic text type.
The label lacks the for="phone" attribute. Tapping the word "Phone" does not focus the input on touchscreens. type="text" prevents mobile phones from opening the numeric telephone keypad. 		Implemented Fix:
Connected label via for="customerPhone" and set type="tel" id="customerPhone" name="customer_phone" autocomplete="tel".
4 <label for="guests">Guests</label><input type="text" id="people"> ID Mismatch between label and input!
The label points to for="guests", but the input has id="people". Screen readers treat the field as completely unlabeled, and clicking the label fails to activate the input. Also accepts invalid text like "two". 		Implemented Fix:
Aligned IDs: <label for="guestsCount"> and <input type="number" id="guestsCount" name="guests_count" min="1" max="20">.
Alternative Fix & Decision:
Alternative: Change the label's attribute to for="people" to match the existing input ID.
Why we chose ours: Standardizing on "guests" (guestsCount) aligns with the café business domain and matches standard database conventions for restaurant table booking.
5 id="date" on lines 10 and 12 Duplicate ID across two different inputs!
Both the date text input and the radio button have id="date". Duplicate IDs violate W3C specifications, create invalid HTML markup, and cause assistive tech to focus the wrong element. 		Implemented Fix:
Assigned globally unique IDs: id="reservationDate" for the date picker and id="seatingInside" for the radio control.
6 <input type="text" id="date" placeholder="dd/mm/yyyy"> Generic text type used for calendar date.
Users must manually type separators like slashes or dots. On mobile devices, no calendar UI appears, resulting in incorrect formats (e.g. mm/dd vs dd/mm) and invalid calendar dates (e.g. 31/02). 		Implemented Fix:
Changed to native type="date" id="reservationDate" name="reservation_date", which opens native OS calendar pickers.
7 <input type="radio" name="inside"> and <input type="radio" name="terrace"> Different name attributes for mutually exclusive radios!
Because their name attributes differ, they do not belong to the same radio group. The user can select BOTH simultaneously, and neither can be deselected! 		Implemented Fix:
Grouped under identical name="seating_area" with distinct values (value="inside" and value="terrace").
8 <input type="radio" ...> Inside (Raw text) Radio inputs lack connected <label> tags.
The text "Inside" and "Terrace" are loose text nodes. On mobile screens, users have to tap the tiny 13px circle directly, causing high tap-target error rates. 		Implemented Fix:
Wrapped each option with <input id="seatingInside"><label for="seatingInside" class="form-check-label">Inside</label> for expanded tap targets.
9 <p>Seating:</p> Radio group lacks accessible semantic container.
A <p> tag does not establish an accessible group association. Screen reader users navigating by form controls jump directly into radio inputs without knowing what "Inside" refers to. 		Implemented Fix:
Replaced paragraph with semantic <fieldset><legend class="form-label">Seating preference</legend>...</fieldset>.
10 <select><option>Lunch</option><option>Dinner</option></select> Missing label, missing name, and missing option values.
Screen readers cannot identify what this select does. Furthermore, without a name attribute, the selected dining time is completely lost upon form submission! 		Implemented Fix:
Added <label for="mealTime">Meal time</label>, added id="mealTime" name="meal_time", and explicit value="lunch" / value="dinner".
11 <textarea placeholder="Comments"></textarea> Missing label, missing id, and missing name.
Screen readers announce only "edit text, multi-line" without context. Once text is typed, the placeholder disappears, leaving the user with no visual cue of the field's intent. 		Implemented Fix:
Added <label for="reservationComments">Comments</label>, id="reservationComments", and name="reservation_comments".
12 <input type="checkbox"> I agree to the terms Unlinked checkbox and missing required constraint.
The text is loose, so clicking the terms text will not toggle the box. In addition, terms of service agreements must be required to ensure legal consent. 		Implemented Fix:
Added id="agreeTerms" name="agree_terms" required and connected <label for="agreeTerms" class="form-check-label">.
13 <div class="btn btn-primary">Reserve</div> Fake button built with a non-interactive <div>!
A <div> is invisible to keyboard Tab navigation, cannot be pressed using Enter or Spacebar, does not fire submit events, does not trigger HTML form validation, and is not announced as a button by screen readers. 		Implemented Fix:
Replaced fake div with semantic <button type="submit" class="btn btn-primary">Reserve Table</button>.
Alternative Fix & Decision:
Alternative: Add tabindex="0", role="button", and custom JavaScript keydown/click handlers to make the <div> emulate a button.
Why we chose ours: Native HTML! A true <button type="submit"> provides native accessibility, built-in keyboard activation, implicit form submission, and native form validation with zero JavaScript overhead.
14 <form> (Missing action and method) Missing form submission attributes.
Without action and method, the form defaults to GET, appending form data into the URL query parameters (which clutters URLs and stores user emails/phones into browser history). 		Implemented Fix:
Added action="#" method="post" to safely handle data submission.
